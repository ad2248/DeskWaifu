# 创建并切换工作树

在新的独立工作树中处理本次调用附带的任务。

1. 若未提供任务描述，先询问要处理的任务，不创建工作树。
2. 检查当前仓库、`git worktree list` 和工作区状态，区分本任务改动与无关改动。如果新工作树需要携带未提交改动，先说明 DSH 的工作树工具会把它们留在原处，并确认具体迁移范围和方式。未经同意不夹带、丢弃或重置改动。
3. 根据任务描述生成简短的英文短横线工作树名及专用分支名，修复使用 `fix/`，功能使用 `feat/`，其他任务使用合适的前缀。名称冲突时选用新名称，不覆盖已有工作树或分支。
4. 确认基线，默认使用仓库默认分支，用户显式指定时使用指定基线。若有 `create_worktree` 且可用同一个 `name` 表达工作树名和分支名，传入 `name` 与已解析的基线提交 `from`，由工具创建工作树并切换会话。否则用 `git worktree add -b <branch> <path> <base>` 创建，再调用 DSH 的 `working_directory`，将 `cd` 设为新工作树的绝对路径。用户显式调用本技能或已要求在新工作树中处理任务时，无需重复确认创建工作树。
5. 创建或会话切换失败时，报告原因及已经创建的工作树或分支，停止实施。调用 `working_directory` 确认会话目录与新工作树路径一致。
6. 核对会话目录、分支、基线和工作区状态，阅读新工作树适用的 `AGENTS.md`。若已获同意携带未提交改动，按确认的范围和方式将改动复制到新工作树，保留原工作树。对照原工作树逐项核验已同意携带的差异及新增文件，包括已有的回归测试。迁移失败、出现冲突或无法确认改动齐全时，停止实施并报告缺项。向用户简要报告工作树路径、分支和后续计划。
7. 在新工作树中继续完成任务：先明确验收标准，阅读相关实现，做最小改动并验证。缺陷修复应补充回归测试；需求存在实质歧义时先询问。遵守当前 agent 与权限限制，Plan 模式下只分析和规划，不实施修改。

不要仅因创建了工作树就停止；应继续处理用户提供的任务。除非用户明确要求，或任务已触发明确包含交付操作的 skill，否则不自动提交、推送或创建 PR。

回归场景：原工作树有已获同意迁移的未提交回归测试。开始实施前，在新工作树核验该测试及其他获同意迁移的改动，保留原工作树中的文件。
