# 修复 PR 审查中的阻塞问题

处理本次调用指定的 PR 审查问题。

接受 PR URL，或当前上下文已明确关联的唯一 PR。目标缺失或有歧义时先询问，不猜测仓库或 PR 编号。

切换工作树前，加载并保留 `submit-code-and-pr` 的提交前检查、验证和推送指令，以便在目标工作树缺少该 skill 时继续。已加载时直接复用。

1. 读取适用的 `AGENTS.md`、存在的 `tea.md` 和提交规范。记录经核验的 PR URL，后续始终使用该 URL 确定目标。仅使用用户提供或上下文已明确的相关工单，不搜索或推断潜在关联。
2. 使用机器上可用的 `gt` 或 `tea` 读取 PR 最新 head/base、全部评审与行内评论、讨论及当前提交的 CI 状态。先查看所选 CLI 的帮助以确认当前版本语法，读取完整的分页结果。区分阻塞问题、非阻塞建议和已失效意见，逐项核对最新代码，不只依赖评审摘要。
3. 检查 `git status`、远端、分支和最近提交，fetch 后确认工作区对应 PR 的源仓库与分支。不得直接在 `main` 上修改。用 `git worktree list --porcelain` 查找可复用的源分支工作树，或用 `git worktree add` 从已核验的源分支创建工作树。使用 `working_directory` 切换到对应工作树的绝对路径。切换后核对会话目录、分支、上游及 PR head，并阅读适用的 `AGENTS.md`。保留用户或其他 agent 的改动，不重置、丢弃、强推或夹带无关修改。
4. 逐项回应评审。按本仓库约定拒绝安全相关建议，并在评审回复中说明决定。将其余确认成立的阻塞问题转为简短修复与验证清单。缺陷尽可能先添加失败的回归测试，再做最小修复；不顺手实现非阻塞建议或扩大需求。意见不成立或需求有歧义时，给出代码与验证证据，必要时向用户询问，不盲目修改。
5. 若目标分支冲突阻塞本次交付，先检查冲突双方意图，再合并 PR 的目标分支并逐项解决；保留双方仍有效的行为，补充组合场景测试。不要用整文件选 ours/theirs 或重写历史来掩盖冲突。
6. 先运行相关测试，再尽可能运行完整构建和测试。检查最终 diff 与 `git diff --check`。未执行或失败的检查如实说明。
7. 采用切换前保留的 `submit-code-and-pr` 指令中的「提交前检查」「验证」「提交并推送」更新现有 PR。只提交本次获授权的改动，使用中文约定式提交。每次推送前必须执行下方「推送前核验」。
8. 在原 PR 中逐项回复阻塞意见，包含对应评审或评论、修复或不修改的理由、验证命令与结果、提交 hash 和已知限制。必要时同步回复明确关联的工单；未解决时说明阻塞与所需输入，不宣称完成。使用可用的 `gt` 或 `tea` 回复对应讨论；所有修改服务端状态的操作显式指定已知的主机、仓库和必要的账号信息，评论使用真实换行。
9. 复查远端 PR 的最新 head、评审回复、CI 状态及本地工作区，向用户报告结果与 PR URL。CI 尚未完成时明确说明；请求重新审查，不擅自批准自己的改动、撤销他人评审、合并 PR 或关闭工单。

## 推送前核验

紧邻推送前重新查询同一 PR 与源远端分支，确认 PR 仍开放、源仓库与分支未变、PR head 和远端分支尖端都等于本次修复所基于的 SHA。确认本地修复基于该提交，显式推送到已核验的源远端与分支。不匹配或推送遭拒时保留本地修复并停止该次推送。不得 amend、跳过钩子或强推。回归场景为测试期间 PR 已关闭但远端分支未变，预期保留本地修复且不推送。
