## 维护规则

1. 先更新对应主题的需求/验收，再记录某次实施及真实结果；不要求两类一一对应。
2. 产品主题使用轻量稳定 ID（如 CFG-03），新条目不复用旧 ID。架构和维护约束可按章节引用，不强制引入管理系统。
3. 新需求写目标、范围/非目标、可观察行为、失败/安全/兼容边界、验收入口、限制和关联日志。代码现状与产品意图不一致时标为待确认，不反向杜撰需求。
4. 日志写背景、身份/源码基线、决策/取舍、实施范围、实际环境/命令/结果及遗留。缺失日期、提交或原始附件时直说，不编造，也不把临时文件描述成持久附件。
5. 同一约束只保留一个权威出处，其他主题补充视角并链接。更新路径后检查文件和锚点；线上、真实设备和云端测试不能因整理文档而自动授权。
