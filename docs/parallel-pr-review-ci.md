# PR 代码审查与 CI 并行执行

PR 创建、重新打开或推送新提交后，两个工作流独立触发：

- `.gitea/workflows/ci.yml` 使用 `pull_request`，负责构建和自动化测试。
- `.gitea/workflows/opencode-review.yml` 使用 `pull_request_target`，从目标分支可信基线加载工作流，并按事件中的 `pull_request.base.sha` 检出目标分支代码及审查脚本，而非固定检出 `main`。两个工作流均未限制 PR 目标分支；CI 另支持手动触发。

审查脚本获取 PR 上下文和 diff，默认不检出 PR head。智能体可通过源码、Git 或 API 补充上下文，并按需构建、测试及检查测试覆盖缺口。临时工作目录不是隔离沙箱：智能体工具权限为全部允许，提示中的不可信输入与禁止修改代码等约束，不构成禁止执行 PR 代码的技术隔离。

审查不等待 CI；提示要求区分本地验证与 CI 结果，发布模板也不声明 CI 已通过。两个 runner 必须分别有可用执行槽位，才能实际同时运行。

## 合并保护

工作流文件本身不会配置分支保护。以下是 Gitea 仓库设置 → 分支 → `main` 的运维要求，不代表远端已经生效：

- 开启状态检查，要求 CI 的精确上下文。预期名称为 `DeskWaifu CI / Arch build and headless Wayland test (pull_request)`；完整格式须从线上 PR 检查或 API 确认后配置，不能仅凭工作流名称推定。
- 至少一次批准，且有效审批者仅限 `Reviewer`。
- 开启 **Ignore stale approvals**：保留历史审查，但旧提交的批准不计入当前提交的合并条件。
- 开启“管理员必须遵守分支保护”，不允许通过绕过名单跳过保护。
- 保持禁止直接推送和强制推送。

审查脚本正常结束只表示结果已处理，不表示通过审查：无批准信号时发布 `COMMENT`，只有明确批准才发布 `APPROVED`。因此不能用审查工作流的绿色状态代替正式批准。

## 验收

以下是上述保护配置生效后的预期验收结果，不是已验证的远端行为：

- CI 失败、排队、运行中或缺失时，即使审查批准，也不能合并。
- CI 成功但 `Reviewer` 尚未批准当前提交时，不能合并。
- CI 成功且 `Reviewer` 批准当前提交后，才满足这两项合并条件；其他分支保护规则仍然适用。
- 推送新提交后必须等待新提交的 CI 和批准。脚本在批准动作及最终发布前检查 head，检测到变化时停止相应操作；最终审查绑定被审查的 `commit_id`。检查与发布不是原子操作，仍有竞态，且此前已创建的 issue 不会撤回，不能保证丢弃所有旧审查副作用。

本地回归测试（不连接模型、不发布审查）：

```sh
python3 -B -m unittest discover -s .gitea/scripts -p 'test_*.py' -v
```

并行触发的线上验收需在工作流进入相应目标分支后，用测试 PR 检查上述场景；验收 `main` 保护时应以 `main` 为目标。`pull_request_target` 会读取目标分支基线工作流，仅修改 PR 来源分支不会激活新的触发方式。

远端实际状态上下文、审批账号与资格、旧批准失效、管理员及绕过规则、直接推送和强制推送限制，以及 runner 槽位和线上触发行为，均未在本次文档核对中验证，需另行检查远端配置和实际 PR。
