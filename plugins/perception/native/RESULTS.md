# ONNX Runtime 原生功能包验证

日期：2026-10-23。本机 CPU：Intel Core Ultra 7 270K Plus，Linux x86_64。

## 模型转换与一致性

- 从姐姐提供的原始 Paddle 模型导出 `small_det + medium_rec`，使用 paddle2onnx 2.0.1、ONNX opset 19，不量化、不使用 ONNX optimizer。
- 导出文件通过 ONNX checker，C++ 使用官方 ONNX Runtime 1.31.0 CPU SDK。SDK 下载校验 SHA-256，导出模型、字典与源文件哈希记录在 manifest。
- `verify_onnx.py` 对检测器两种宽高、识别器两种宽度以及 batch=2 输入进行原始张量对照。检测输出最大绝对误差约 `2.88e-6`；识别约 `3.31e-5`。5 组均通过 `atol=1e-4, rtol=1e-3`。
- 四类 960×640 合成图与此前 Python/Paddle 流水线输出的文字行、行序和文字（含空格）一致。空白图无误检。不同前后处理实现仍产生坐标与置信度差异：本轮最大顶点坐标差 2px，最大置信度差约 0.01634。
- C++ 用浮点矩形扩张实现 DB quad unclip，而 Python 用 pyclipper 整数 round offset；并非逐位等价。对斜字、复杂桌面、长文本与极端比例图片尚未建立准确率结论。

## 性能：没有获得速度优势

以下为已解包归档中 C++ 程序的独立实测，不需要 Python/Paddle 环境。CPU 两线程，识别框逐行推理，ORT 开启图优化。每图连续 3 次，热推理均值取后两次。

| 合成图 | C++ 首次推理 | C++ 热推理均值 | 此前 Python 热推理均值 |
| --- | ---: | ---: | ---: |
| light，3 行 | 3.306s | 3.283s | 0.866s |
| dark-small，3 行 | 2.970s | 2.970s | 0.817s |
| dense，18 行 | 17.362s | 17.265s | 3.797s |
| blank | 0.328s | 0.327s | 0.354s |

这不是纯粹的推理引擎公平对照：Python 流水线可批量识别，当前 C++ 逐行执行；图优化与算子实现也不同。只能说明**当前实现较慢，不能把换成 C++/ONNX 宣称为性能优化**。后续优先调查识别批处理与算子耗时，而非直接增加线程或默认启用 GPU。

同一辅助进程完成协议错误请求、四类图各 3 次及 JPEG 请求，Linux 子进程峰值 RSS 约 429 MiB。尚无长时运行/泄漏结论，也不能与旧测试不同工作负载下的峰值直接作严格比较。

## 部署与通信

- 已构建 CPack TXZ 可选归档，包含模型、ORT CPU 库、字典、清单和许可证；约 79 MiB 压缩体积（构建产物存于忽略目录，不提交）。这是本机 ABI 的开发包，不是已经发布的 Arch 包或跨发行版通用包。
- 从归档解压的辅助程序，在只保留 PATH/LANG 的环境中完成推理，未设置 Python 环境、模型缓存或 LD_LIBRARY_PATH；模型与 ORT 均从包内相对路径加载。
- 主程序 ELF 依赖没有 ONNX Runtime、OpenCV 或 Paddle；推理运行库仅由辅助程序加载。
- 独立 QtCore 客户端测试覆盖：未安装、不可执行启动失败、按需启动、busy 拒绝、ID/版本/结果校验、超大或损坏消息、超时、取消、子进程退出、任务错误、空闲退出与重启、最近一条结果保留。
- 原生 helper 测试覆盖四类图、JPEG、错误后继续服务、超大请求、版本错误、超限图片、动画图片和 EOF。测试脚本还校验了篡改字典后拒绝加载。
- 在私有 KWin virtual 会话运行真实桌宠，经原 Unix socket → AppCommandHandler → OcrClient → 解包布局 helper → 实际 ONNX 推理 → 结果查询闭环通过；未安装包时桌宠仍可启动。取消任务、强制终止本测试自己的 worker 后重新请求均成功。
- OCR 进行中查询主程序 `get_status` 实测约 19ms；不代表所有机器的延迟保证。
- 常规主程序构建及原有 CTest：74 项通过，1 项 offscreen-renderer 因环境跳过。无推理依赖进入常规构建/CI；OCR 专项测试均手动运行。
