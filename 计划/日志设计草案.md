# DeskWaifu 日志设计草案

草案适用于当前 Rust workspace 的宿主、OS IPC 和进程内动态插件。文中的配置参数为建议初值。

## 1. 现状与目标

- 宿主在 Tokio `current_thread` 上加载插件并驱动 OS 主循环。插件回调、tick 和 IPC 命令串行运行，日志写入阻塞会拖延后续请求和退出处理。 [宿主入口](../apps/deskwaifu/src/main.rs#L17) · [OS 主循环](../crates/os/src/host.rs#L10)
- 插件初始化失败及其清理失败、IPC 就绪、客户端注册失败目前由几个独立的 `eprintln!` 输出。启动和运行中的致命错误则通过返回值上报。 [插件初始化](../crates/runtime/src/lib.rs#L181) · [IPC 就绪](../crates/os/src/host.rs#L64) · [客户端注册](../crates/os/src/async_server.rs#L44)
- 首期统一日志入口，让用户能从启动、插件失败、IPC 就绪和退出事件中定位故障阶段。命令结果继续由 `deskwaifucli` 输出，宿主诊断统一写入宿主的 `stderr`。 [CLI 入口](../apps/deskwaifucli/src/main.rs#L13)

## 2. 组件职责

| 组件 | 职责 |
| --- | --- |
| `apps/deskwaifu` | 在加载插件前安装 `tracing_subscriber`，读取过滤配置，持有日志写入线程并控制退出刷新期限。 |
| `crates/os` | 记录 IPC 就绪、协议拒绝类别、客户端注册故障及退出信号。传输层记录协议事实，由 runtime 记录命令执行结果。 |
| `crates/runtime` | 记录动态加载和插件生命周期事件、注册命令的执行结果及耗时，将插件日志转发给宿主。 |
| `crates/sdk` | 提供动态库的日志转发器和初始化入口；插件业务代码直接使用 `log` 宏。 |
| `deskwaifucli` | 保持命令输出、错误提示和退出码的现有行为。 |

宿主、OS 和 runtime 继续用 `tracing` 记录结构化事件。每个动态插件内的 `log` 通过 SDK 提供的转发器进入同一个宿主输出队列。 [动态插件部署约定](../README.md#L71)

## 3. 事件、级别与数据约定

| 级别 | 主要事件 | 建议字段 |
| --- | --- | --- |
| `ERROR` | `host.failed`、`plugin.stop_failed` | `phase`、`error_kind`、可用时的插件身份或 `errno` |
| `WARN` | `plugin.initialize_failed`、`ipc.client_registration_failed`、`logging.dropped` | 插件身份、`error_kind`、`dropped_count` |
| `INFO` | `host.starting`、`plugins.loaded`、`ipc.ready`、`host.shutdown_requested`、`host.stopped` | `version`、`plugin_count`、`socket_path`、`signal`、`result` |
| `DEBUG` | `command.completed`、`ipc.request_rejected` | `command`、`result`、`duration_ms` 或 `reason` |
| `TRACE` | `plugin.callback_completed` | 插件身份、`phase`、`duration_ms` |

- 每条记录包含 UTC 时间和级别。宿主结构化事件另外包含固定 `target`、稳定的 `event` 名及白名单字段。插件日志只需要宿主标记的插件身份、模块（没有模块时用 `log` target）和消息，不要求定义结构化事件。`ipc.ready` 在 socket 绑定、退出信号注册和插件启动全部成功后记录。
- 在能识别故障的层记录错误阶段与类别，例如 `phase=socket_bind`、`error_kind=address_in_use`。入口根据返回结果设置退出码，避免 Rust 入口自动向 `stderr` 再打印原始错误。首个故障和随后发生的清理故障分别记录，退出汇总只记录结果。
- 采用字段白名单。命令名只取已注册名称，未知命令记录 `unknown_command`。日志字段排除 IPC 参数和响应正文、剪贴板、截图、OCR 文本、音频、凭据以及插件返回的任意错误文本。插件使用日志宏时同样应只输出排障所需的固定说明、计数和状态类别；宿主不会尝试从自由文本中识别和清除敏感内容。协议错误归为固定类别，普通无效请求在 `DEBUG` 可见。
- 对重复发生的客户端注册失败按事件类别限频，并报告被合并次数。成功 tick 和消息回调只在 `TRACE` 下记录。

## 4. 输出、背压与退出

### 首期输出

默认以紧凑文本写入 `stderr`，级别为 `INFO`。首版 `RUST_LOG` 支持全局级别、`target=级别` 和 `off`。最具体的目标前缀优先。宿主目标如 `deskwaifu::host`、`deskwaifu::ipc`、`deskwaifu::runtime`；插件在宿主侧使用 `deskwaifu::plugin::<动态库文件名去掉 lib 前缀和 .so 后缀>::<log target>` 作为过滤目标，默认 `log target` 为模块路径。由同一份宿主配置决定两个入口是否接收记录。无效配置回退到默认过滤器，并报告一次配置错误。

```sh
RUST_LOG=info,deskwaifu::ipc=debug,deskwaifu::plugin::deskwaifu_test_plugin=debug deskwaifu
```

### 写入线程与队列

- 调用线程用于过滤、生成大小受限的记录和尝试入队。专用线程负责向 `stderr` 写入。队列保存宿主拥有的记录；插件转发回调返回前已完成格式化，不保留指向动态库的借用。
- 建议容量为 1,024 条，每条编码后最多 4 KiB，包含行终止符。对字段及消息使用有界格式化，转义换行并保留有效 UTF-8 和行终止符；禁止先把整条无界消息格式化成字符串再截断。容量和单条限制为记录正文提供约 4 MiB 的上界，队列元数据和写入缓冲另计。
- 队列满时丢弃新记录并累计数量。写入恢复后由写入线程直接输出 `logging.dropped` 摘要，避免摘要再次参与争抢队列。
- `SIGINT`、`SIGTERM` 和常规错误退出先结束宿主运行和资源清理，再关闭日志生产并等待刷新，建议最多 1 秒。达到期限后进程按原有结果退出。管道长期阻塞、队列溢出或进程被强制终止时，未写入的记录可能丢失。退出实现需保证等待路径和析构路径都不会无限等待写入线程。

### 可选文件输出

桌面启动需要保留诊断历史时，可用 `DESKWAIFU_LOG_FILE=1` 启用文件输出。默认位置为 `$XDG_STATE_HOME/deskwaifu/logs`，该变量为空、未设置或为相对路径时使用 `~/.local/state/deskwaifu/logs`。建议按大小轮转，每个文件最多 5 MiB，保留当前文件及最多四份归档。目录和文件仅限当前用户访问。文件创建或写入失败时继续提供 `stderr` 输出，文件目的地也应采用有界写入，避免文件写入拖住 `stderr` 或 IPC。

## 5. 接口与使用示例

以下 Rust 代码为接口草案。插件只使用常见的 `log` 宏，加载器和 SDK 封装动态库之间的转发。

### 5.1 插件调用示例

插件直接依赖 `log = "0.4"`，沿用 `export_plugin!`，在业务代码里调用 `log` 宏即可。以下示例仍保持测试命令的原样回显行为，仅把参数个数写进日志。 [测试插件](../plugins/test-plugin/src/lib.rs#L15)

```rust
fn test_command(args: &[String]) -> Result<String, String> {
    log::debug!("执行 test 命令，参数个数={}", args.len());
    Ok(format!(
        "test command received {} argument(s): {:?}",
        args.len(), args,
    ))
}
```

普通函数、`stop` 和 worker 线程均可直接调用这些宏。runtime 另在现有命令派发点记录结构化的 `command.completed`，包含已注册命令名、结果类别和耗时。不记录原始参数、响应或未知命令的原始名称。 [命令派发](../crates/runtime/src/lib.rs#L233)

### 5.2 SDK 导出入口和转发接口

独立的 `.so` 可能各自持有 `log` 的全局状态。SDK 的 `export_plugin!` 为动态部署同时生成 `deskwaifu_plugin_init_logging`，在插件所在动态库注册一次转发器；现有 `deskwaifu_plugin_create` 签名不变。这是宿主与插件联合构建时使用的内部 Rust ABI，不是稳定 C ABI。 [导出宏](../crates/sdk/src/lib.rs#L5)

```rust
// SDK 内部类型。SourceId 是加载器分配的日志来源标识，不是 PluginId。
pub type SourceId = u64;

#[derive(Clone, Copy)]
pub struct PluginLogBridge {
    pub source: SourceId,
    pub enabled: fn(SourceId, &log::Metadata<'_>) -> bool,
    pub emit: fn(SourceId, &log::Record<'_>),
}

#[derive(Debug)]
pub enum InitLogError {
    AlreadyInstalled,
}

pub const PLUGIN_INIT_LOG_SYMBOL: &[u8] = b"deskwaifu_plugin_init_logging\0";
pub type PluginInitLog = fn(PluginLogBridge) -> Result<(), InitLogError>;

impl log::Log for PluginLogBridge {
    fn enabled(&self, metadata: &log::Metadata<'_>) -> bool {
        (self.enabled)(self.source, metadata)
    }

    fn log(&self, record: &log::Record<'_>) {
        // log 宏不保证提前调用 enabled，因此转发之前再判断一次。
        if self.enabled(record.metadata()) {
            (self.emit)(self.source, record);
        }
    }

    fn flush(&self) {} // 插件不等待宿主刷新输出。
}
```

生成的入口将 `PluginLogBridge` 保存到动态库内的 `OnceLock`，调用 `log::set_logger` 注册，并将该库的 `log::set_max_level` 设为 `Trace`，实际过滤由宿主完成。插件不自行注册其他全局 logger。重复初始化或已有 logger 时返回错误。静态链接测试无需调用该入口；更新后的动态插件需与宿主联合重建。宏展开的入口示意如下：

```rust
#[unsafe(no_mangle)]
pub fn deskwaifu_plugin_init_logging(bridge: PluginLogBridge) -> Result<(), InitLogError> {
    static BRIDGE: std::sync::OnceLock<PluginLogBridge> = std::sync::OnceLock::new();
    BRIDGE.set(bridge).map_err(|_| InitLogError::AlreadyInstalled)?;
    log::set_logger(BRIDGE.get().expect("bridge initialized"))
        .map_err(|_| InitLogError::AlreadyInstalled)?;
    log::set_max_level(log::LevelFilter::Trace);
    Ok(())
}
```

实际宏通过 SDK 的隐藏重导出引用 `log`，使转发器和插件的 `log` 宏使用 workspace 统一的依赖版本。导出符号处沿用现有插件入口的 lint 处理。

### 5.3 runtime 加载与宿主接收

runtime 打开动态库并解析入口后，按库名登记日志来源，再绑定日志转发器，最后调用构造函数。这样构造、命令回调和后台线程的日志都能归属到同一来源；构造前尚不知道的插件名称不影响标记。来自动态库加载器、早于初始化入口的日志不在覆盖范围内。以下为现有加载器中的代码片段。 [动态加载器](../crates/runtime/src/dynamic.rs#L25)

```rust
// init_log: 已解析的 PluginInitLog；create: 已解析的 PluginCreate。
// source_guard 在失败时回收登记，成功后与动态库句柄一起交给 runtime。
let source_guard = plugin_logs::register_source(path)?;
init_log(PluginLogBridge {
    source: source_guard.id(),
    enabled: plugin_logs::enabled,
    emit: plugin_logs::emit,
})
.map_err(|_| "plugin logger initialization failed")?;
let plugin = create();
let id = self.add_boxed(plugin)?;
// 此时才有 PluginId；可在后续记录补充该身份。
source_guard.bind_plugin(id);
```

宿主转发函数可在任意线程调用，使用线程安全的过滤配置和有界入队，不依赖线程局部 subscriber。`emit` 直接进入宿主输出队列，不再调用全局 `log`，避免循环转发。`log::Record` 及其内部引用只在回调期间有效；队列没有插件持有的对象、引用或析构函数。停止时先等插件 worker 退出，保留转发至插件实例和动态库清理完毕，再撤销来源登记。缺失初始化符号或注册失败作为动态插件加载错误处理。

### 5.4 宿主初始化和关闭接口

宿主内部的日志模块拟提供以下签名。`install` 装配过滤器、subscriber、插件日志接收入口和共享写入线程。`shutdown` 消费句柄，关闭入队并在指定期限内等待写入线程确认刷新。期限到达时可以释放线程句柄以结束进程。句柄的析构路径应立即返回。

```text
logging::install() -> Result<Logging, InitError>
Logging::shutdown(self, timeout: Duration) -> FlushOutcome
FlushOutcome = Flushed | TimedOut | WriterFailed
```

主程序先安装日志，再进入现有启动流程。下面的 `run_host` 表示从现有入口提取的启动函数。参数拒绝和插件加载失败由该函数记录。OS 和 runtime 记录各自能识别的故障，入口只记录结束汇总。 [宿主入口](../apps/deskwaifu/src/main.rs#L17)

```rust
use std::{process::ExitCode, time::Duration};

#[tokio::main(flavor = "current_thread")]
async fn main() -> ExitCode {
    let logger = match logging::install() {
        Ok(logger) => logger,
        Err(_) => {
            // 启动尚未建立写入线程，仅尝试发出固定的启动诊断。
            logging::report_init_failure();
            return ExitCode::FAILURE;
        }
    };
    tracing::info!(
        target: "deskwaifu::host",
        event = "host.starting",
        version = env!("CARGO_PKG_VERSION"),
    );
    let result = run_host().await;
    tracing::info!(
        target: "deskwaifu::host",
        event = "host.stopped",
        result = if result.is_ok() { "ok" } else { "failed" },
    );
    let _ = logger.shutdown(Duration::from_secs(1));
    if result.is_ok() { ExitCode::SUCCESS } else { ExitCode::FAILURE }
}
```

`report_init_failure()` 也属于宿主内部接口，供日志初始化发生不可恢复故障时使用。固定诊断采用可立即返回的尽力输出。退出码始终反映宿主启动和运行的结果。

SDK 接口变更随宿主和动态插件一起构建，用实际加载的 `.so` 验证日志归属。 [部署与构建约定](../README.md#L71)

## 6. 实施与验收

- [ ] **首期统一宿主日志。** 接入 subscriber、有界写入和退出刷新，替换现有 `eprintln!`。用宿主进程测试验证无效插件库和 socket 占用的错误事件、退出码和就绪事件顺序。用 runtime 测试验证单个插件初始化失败后其余插件仍可服务，以及失败后的清理错误能单独定位。
- [ ] **验证默认输出与退化行为。** 检查 `RUST_LOG` 过滤、无效配置回退和 CLI 原有输出。向正常命令及畸形请求注入标记，验证标记不出现在宿主的 `DEBUG` 或 `TRACE` 日志。用可控阻塞的写入端压满队列，验证容量上限、恢复后的丢弃摘要、IPC 响应及 `SIGTERM` 的退出时限。
- [ ] **接入动态插件日志。** 联合构建两个真实 `.so`，验证构造、普通命令函数、worker 和停止阶段均可通过 `log` 宏发出日志，且按正确来源归属。对其中一个插件或模块开启 `DEBUG`，确认另一个仍按默认级别过滤；另验证缺失初始化入口时有明确错误，且正常卸载后宿主拥有的排队记录仍能写出。
- [ ] **按桌面需求补充文件输出。** 以临时状态目录验证开关、轮转、保留上限、权限及不可写目录下的降级行为。
